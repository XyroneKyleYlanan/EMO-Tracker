Risk Assessment and Analysis — EMO Tracker

How to use: Select the table below, copy (Ctrl+C), and paste into Word or Google Docs. It pastes as a native table. Risk Level is derived from a standard Likelihood × Impact matrix, rated before mitigation. The mitigations describe what the system and the team do now (updated October 7, 2026).

Risk ID Risk Description Category Likelihood Impact Risk Level Mitigation Strategy
R1 Server laptop failure or downtime, making the system inaccessible to all users Technical Medium High High Keep the server laptop plugged in and charged during office hours (the battery acts as a built-in UPS); starting the system is a double-click on the start file; documented setup steps (README) let another laptop take over, and the latest backup can be restored on it.
R2 Data loss from laptop failure or theft, accidental deletion, or a faulty update Data Medium High High Automatic daily backups of the database and all uploaded documents (made on the first use each day; the newest 14 are kept, plus named snapshots that are never deleted automatically); backups can be stored on a USB drive (BACKUP_PATH); the administrator's Home shows the last backup, or a warning if backups fail; a backup is saved automatically before database updates; a restore command brings back all data and documents.
R3 Network (WiFi or hotspot) unavailability preventing devices from reaching the server Technical Medium High High Use a dedicated router or mobile hotspot; the system needs only a local network, not internet access; the office laptop itself can still use the system; when a device can't connect, the app says "Can't reach the EMO Tracker server" and offers Try again, and no data is lost.
R4 Single point of failure — the database, backend, and frontend all run on one device Technical Low High Medium Documented setup and update steps (README) so the system can be redeployed on another machine; backups restore on any machine (older backups are brought up to the current database structure); the Windows start file finds Laragon's PHP by itself.
R5 Unauthorized access through shared, guessed, or leftover credentials Security Low High Medium Role-based access checked by the backend on every request; login limited to 10 attempts a minute per account and device; passwords hashed with bcrypt; deactivating a departed member signs them out immediately; changing a password signs out the account's other devices; the demo accounts (with a published demo password) are replaced by real accounts before the EMO uses the system.
R6 Administrator account compromise, granting full control of the system Security Low High Medium Keep administrator accounts few (the office head and one backup); use strong, unshared passwords; an administrator can't deactivate or demote themselves, so an active administrator always remains; error messages never reveal technical details about the server.
R7 Double-booking: two events booked at the same venue and time Operational Medium Medium Medium The event form warns while the venue, date and time are chosen; the event panel and the Schedule ("Overlap" label) show clashes to everyone; a managed venue list keeps names consistent so clashes can be detected. It is a warning, not a block, since some overlaps are intended; places typed as free text aren't checked.
R8 User resistance to adopting the new system over the familiar spreadsheet Operational Medium Medium Medium The Schedule page is laid out like the EMO's own sheet (one tab per year, colored by building); the EMO's existing schedule is imported so no re-typing is needed; Excel export keeps the familiar format; hands-on orientation during the pilot.
R9 Users forgetting passwords; the system has no self-service password reset Operational Medium Low Low Administrators reset passwords in Staff Management; users change their own password once logged in; self-service (email) reset is a future enhancement, since the system runs without internet.
R10 Incorrect or inconsistent data entry (e.g., wrong dates, times, or venue names) Operational Medium Medium Medium Server-side validation (an end date can't be before the start date; an end time must be after the start time); venues chosen from a managed list; department suggestions; when a date or time changes, the form asks whether it was a reschedule or a correction; cancelling is reversible; text cleanup makes names and rooms consistent.
R11 Errors when migrating the EMO's hand-typed spreadsheet into the system Data Medium Medium Medium A dry run checks the file before anything is saved; rows that can't be read with confidence are listed for a person to review instead of being guessed; running the import twice never duplicates events; a snapshot is taken before importing; the final import uses the EMO's latest sheet.
R12 Accidental deletion of events, documents, or other records Data Low Medium Low Confirmation before every deletion; only the administrator can delete events and documents; completed events lock their tasks for other roles; people are deactivated, never deleted; daily backups allow recovery.
R13 A new version of the code runs on a database that hasn't been updated, causing errors Technical Low High Medium The start files (start.bat, start.command) apply any database changes automatically each time the system starts, after saving a backup; if the update can't be applied, the system doesn't start and says why.
R14 Concurrent editing conflicts when two users change the same record Technical Low Medium Low The small office (about 5–10 members) makes simultaneous edits unlikely, and event details have one editor (the administrator); if a record was deleted meanwhile, the user gets a plain "This item no longer exists" message; record-level locking is a future enhancement.
R15 Exposure of the EMO's real data through the public code repository Security Low Medium Low Real schedule data is kept only in the local database and never committed; screenshots and documentation use demo data or totals only; the import's review list is saved in private storage.
R16 Scope changes arising from panel or client feedback during development Project Medium Medium Medium Develop in defined phases; confirm added features with the adviser (the professor allowed more than four features if they fit the client's needs); record every approved change and its reason in the project's decision log (ROADMAP.md) for traceability.
Risk Level Legend:

High Requires immediate, priority mitigation.
Medium Should be monitored and mitigated during development.
Low Acceptable; managed with standard practices.

Risk Level matrix: Likelihood (Low / Medium / High) × Impact (Low / Medium / High). Medium or High likelihood with High impact yields High risk; Low likelihood with High impact, or Medium with Medium, yields Medium; lower combinations yield Low.
